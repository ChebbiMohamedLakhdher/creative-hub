Project title:
    CreativeHub - A community platform for discovering and sharing creative work

Repository:
    creative-hub

Technology:
    Next.js 14, React, TypeScript, Tailwind CSS, Prisma, PostgreSQL,

Document purpose:

1. PROJECT OVERVIEW
===================

CreativeHub is a full-stack web platform designed for creators who want to
publish, organize, discover, and discuss creative work. The platform supports
different types of digital content, including:

    - 3D models
    - Images
    - Audio files
    - PDF documents

The main idea is to create a shared creative space where users can:

    - Create an account and manage a profile.
    - Upload creative projects.
    - Present their work in a personal portfolio.
    - Discover projects from other creators.
    - Search and filter content.
    - Like projects and follow other users.
    - Comment on projects.
    - Exchange private messages.
    - Participate in forum discussions.
    - Receive notifications about relevant activity.
    - Use a natural-language discovery tool to find useful inspiration.

The application is intended to be useful for designers, developers, 3D
artists, photographers, audio producers, illustrators, students, and other
creative professionals.


2. MAIN OBJECTIVES
==================

The objectives of the project were:

    1. Build a modern and responsive web application.
    2. Allow users to share different kinds of creative work.
    3. Store application data in a structured relational database.
    4. Provide a safe authentication and authorization flow.
    5. Create a useful project discovery experience.
    6. Add community features such as forums and messaging.
    7. Make the application easy to run locally and in a deployment
       environment.
    8. Add automated quality checks through continuous integration.
    9. Populate the database with realistic test data.
   10. Document the setup, architecture, and operational procedures.


3. APPLICATION ARCHITECTURE
===========================

The application uses the following architecture:

    Browser
        |
        v
    Next.js App Router
        |
        +--> Clerk authentication
        |
        +--> API routes
        |
        +--> Application services in lib/
        |
        +--> Prisma ORM
        |
        v
    PostgreSQL database

Uploaded files are stored under the local public/uploads directory during
the current phase. In Docker, uploads are stored in a persistent named
volume so they survive container recreation.

The application is organized into the following important areas:

    app/
        Pages, layouts, loading states, error states, and API routes.

    components/
        Reusable interface components, community components, viewers, and
        administration components.

    lib/
        Database access, authentication helpers, storage logic, community
        services, notifications, validation, and search logic.

    prisma/
        Database schema and migration history.

    public/
        Static assets and uploaded files.

    .github/workflows/
        Continuous integration configuration.

5. FEATURES IMPLEMENTED
=======================

5.1 Authentication and profiles
-------------------------------

The application integrates Clerk for authentication. Users can sign up and
sign in through the configured Clerk pages. The application synchronizes
authenticated Clerk profiles with the local User table.

User profiles contain:

    - A unique username
    - A Clerk identifier
    - An avatar
    - A biography
    - Creation and update timestamps

Users can access their own profile, view other users, and see projects
associated with a creator.

The application also contains protected functionality for:

    - Creating projects
    - Editing a profile
    - Uploading files
    - Sending messages
    - Creating forum topics and replies
    - Liking projects
    - Accessing administrative features


5.2 Creative project uploads
----------------------------

Users can upload projects through a drag-and-drop interface. The upload
system validates:

    - The selected category
    - The file extension
    - The MIME type
    - The maximum file size
    - Optional preview image validity

The maximum upload size is 50 MB.

Supported categories and examples include:

    3D:
        GLB and GLTF files.

    Image:
        JPG, JPEG, PNG, GIF, WEBP, SVG, and AVIF files.

    Audio:
        MP3, WAV, OGG, M4A, and FLAC files.

    PDF:
        PDF documents.

Projects have:

    - A title
    - A description
    - A category
    - A media URL
    - An optional thumbnail or preview
    - A visibility state
    - A moderation status
    - Like and view counters
    - Creation and update timestamps


5.3 Category-specific viewers
-----------------------------

The project detail pages use different viewers depending on the content type:

    - 3D viewer for GLB and GLTF models.
    - Image gallery for image projects.
    - Audio player for audio content.
    - PDF viewer for PDF documents.

This makes the project detail page appropriate for the uploaded content
instead of treating every project as a generic file.


5.4 Project discovery
---------------------

The home page contains:

    - Latest projects
    - Trending projects
    - Category filters
    - Text search
    - Pagination and load-more behavior
    - Responsive project cards

The project listing supports filtering by:

    - Category
    - Search text
    - User
    - Latest or trending order

The database query only returns active and public projects for the public
discovery pages.


5.5 Likes, views, comments, and activity
----------------------------------------

Users can like and unlike projects. Likes are protected by a unique
constraint on the combination of user and project, preventing duplicate
likes.

The application records:

    - Project views
    - Project likes
    - Unlike events
    - Comments
    - Shares

Daily view aggregates are also stored to support future analytics while
keeping the raw view event history available.

Comments support replies through a self-referencing relation.


5.6 Following and notifications
-------------------------------

Users can follow other creators. Follow relationships are protected by a
unique constraint so that the same relationship cannot be inserted twice.

Notifications can be generated for activities such as:

    - Likes
    - Messages
    - Forum replies
    - Other user activity

Notifications have recipients, optional actors, optional project references,
optional comment references, optional topic references, read state, and
timestamps.


5.7 Forums and community discussions
------------------------------------

The community area contains forum topics and replies.

A forum topic includes:

    - An author
    - A title
    - A body
    - Creation and update timestamps
    - A collection of replies

A forum post includes:

    - The topic it belongs to
    - Its author
    - Its body
    - Creation and update timestamps

The community routes allow users to:

    - List discussion topics
    - Open a topic
    - Create a topic
    - Reply to a topic
    - Receive a notification when a topic receives a reply


5.8 Private messages
--------------------

The messaging system supports direct conversations between two users.

Conversations use a normalized pair of user IDs so the same two users share
one conversation regardless of who starts it.

Messages include:

    - A sender
    - A recipient
    - A conversation
    - Message text
    - Creation timestamp
    - Read timestamp

Unread messages are marked as read when the conversation is opened.


5.9 Administrative functionality
--------------------------------

The project includes administrative routes and dashboard components for
managing platform activity. The data model includes support for:

    - Reports
    - Report statuses
    - Project moderation statuses
    - Audit logs
    - Administrator identifiers

This provides a foundation for reviewing reported content and tracking
administrative actions.


6. DATABASE IMPLEMENTATION
==========================

The initial application used JSON storage for early development and migration
purposes. The project was moved to PostgreSQL with Prisma to provide:

    - Relational data integrity
    - Foreign key constraints
    - Unique constraints
    - Typed database queries
    - Better support for concurrent users
    - A clear migration history
    - A path to deployment on managed PostgreSQL services

Important database models include:

    User
    Category
    Project
    Tag
    ProjectTag
    Like
    View
    ViewDailyAggregate
    Comment
    Follow
    Notification
    Report
    ProjectEvent
    AuditLog
    Conversation
    Message
    ForumTopic
    ForumPost

Important data integrity rules include:

    - Unique Clerk IDs.
    - Unique usernames.
    - Unique user/project likes.
    - Unique follower/following pairs.
    - Unique conversation user pairs.
    - Foreign key relationships with cascading behavior where appropriate.

Important indexes include:

    - Project category and creation date.
    - Project status and visibility.
    - Likes by project.
    - Views by project and date.
    - Messages by conversation and creation date.
    - Messages by recipient and read state.
    - Forum topics by creation date.
    - Forum posts by topic and creation date.

8. NATURAL-LANGUAGE DISCOVERY SEARCH
====================================

An AI-style discovery feature was added after selecting a no-cost local
approach instead of using an external AI provider.

The feature is available from the home page under:

    Find inspiration for your next project

The user can describe an idea, for example:

    "I need an ambient soundtrack for a short film"

The system then:

    1. Normalizes the user query.
    2. Removes common stop words.
    3. Expands selected terms using a local synonym map.
    4. Detects likely project categories.
    5. Loads active and public projects from PostgreSQL.
    6. Scores project titles, descriptions, categories, and tags.
    7. Applies an additional score for a matching category.
    8. Sorts projects by relevance.
    9. Returns a small list of suggestions.
   10. Explains why each result was selected.

Examples of local term expansion:

    ambient:
        sound, audio, music, field, recording

    architecture:
        architectural, building, house, space, courtyard

    branding:
        brand, identity, logo, mark

    generative:
        procedural, creative, code, interactive

    typography:
        type, font, editorial, poster

The API route is:

    GET /api/discover?q=your-description

The implementation is located in:

    lib/ai-search.ts
    app/api/discover/route.ts

This approach is intentionally local and transparent. It does not send user
queries or project data to an external AI service and does not require an
external API key.

Future versions could replace or extend the local ranking logic with semantic
embeddings, vector search, or an external language model while keeping the
same API contract.


9. DEVOPS AND CONTAINERIZATION
==============================

Docker support was added to make the application easier to run consistently.

The Dockerfile uses a multi-stage build:

    1. Dependency stage:
       Installs npm dependencies.

    2. Builder stage:
       Generates the Prisma client and creates the Next.js production build.

    3. Runner stage:
       Copies only the runtime files and starts the application as a
       non-root user.

The production container:

    - Uses Node.js 20 Alpine.
    - Uses Next.js standalone output.
    - Runs Prisma migrations before starting Next.js.
    - Exposes port 3000.
    - Persists uploads through a mounted volume.

Docker Compose provides two services:

    db:
        PostgreSQL 16 Alpine.

    app:
        The CreativeHub production application.

The database service has a health check using pg_isready. The app waits until
the database is healthy before starting.

Named Docker volumes are used for:

    - PostgreSQL data.
    - Uploaded files.

Useful commands:

    docker compose --env-file .env.local up --build
        Build and start the full application.

    docker compose ps
        Show service status.

    docker compose logs -f app
        Follow application logs.

    docker compose down
        Stop containers while preserving volumes.

    docker compose down -v
        Stop containers and remove stored database/upload volumes.

An important issue encountered during Docker setup was running a manually
created container outside Compose. That container did not receive
DATABASE_URL and stopped during Prisma startup. The issue was diagnosed by
checking docker ps, docker inspect, and docker logs. The correct solution was
to use the Compose-managed services and provide the correct environment file.

Another issue was that the Clerk publishable key is embedded during the
Next.js production build. Passing the key only at container runtime was not
sufficient. The Docker build was updated to accept the key as a build
argument, and the Compose command was updated to load .env.local.

12. PROBLEMS ENCOUNTERED AND SOLUTIONS
======================================

Problem 1: Missing external image host configuration
----------------------------------------------------

Next.js rejected remote thumbnail URLs from picsum.photos and avatar URLs from
api.dicebear.com because they were not configured in next.config.mjs.

Solution:

    Added both hosts to the Next.js images.remotePatterns configuration and
    restarted the development server.

Lesson:

    Next.js Image optimization requires every external image hostname to be
    explicitly configured.


Problem 2: Prisma DATABASE_URL error
------------------------------------

Prisma reported:

    Environment variable not found: DATABASE_URL

Cause:

    Prisma was executed from a process or container where DATABASE_URL had not
    been defined.

Solution:

    - Confirmed that Prisma loads .env from the project root.
    - Added explicit PowerShell setup instructions.
    - Configured Docker Compose to pass DATABASE_URL to the app.
    - Used localhost for host-side Prisma commands.
    - Used db as the hostname inside the Compose network.

Lesson:

    Host and container environments use different database hostnames. The
    database service name works inside Compose, while localhost is required
    from the Windows host.


Problem 3: Standalone Docker container stopped
----------------------------------------------

A container named sweet_wescoff exited with status 1 because it was started
manually without Compose environment variables. Its logs showed the same
missing DATABASE_URL Prisma error.

Solution:

    - Inspected the container with docker inspect.
    - Read the failure with docker logs.
    - Confirmed the Compose services were healthy.
    - Switched to the Compose-managed app and database services.

Lesson:

    Production containers should be started through the documented Compose
    configuration so dependencies, networks, health checks, and environment
    variables are provided consistently.


Problem 4: Invalid Clerk key in production middleware
-----------------------------------------------------

The application initially returned a 500 error because Docker used placeholder
Clerk values. The Next.js middleware rejected the invalid publishable key.

Solution:

    - Loaded the local environment file for Compose.
    - Passed NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY as a Docker build argument.
    - Rebuilt the production image.
    - Verified the application returned HTTP 200.

Lesson:

    Public Next.js environment variables may be embedded during build time.
    Runtime environment configuration alone may not be sufficient for values
    used by middleware or client-side code.


Problem 5: Seed script missing in production image
-----------------------------------------------

The production Docker image does not include TypeScript source files, so
running npm run seed:demo inside the production container failed because
lib/scripts/seed-demo.ts was not present.

Solution:

    Executed the seed from the host against the exposed PostgreSQL port:

    $env:DATABASE_URL="postgresql://creative_hub:creative_hub_dev@localhost:5432/creative_hub"
    npm run seed:demo

Lesson:

    Development and data-management scripts should be kept separate from the
    minimal production runtime image, or provided through a dedicated
    maintenance image or one-off migration job.


13. SECURITY AND RELIABILITY CONSIDERATIONS
===========================================

The project includes several security and reliability practices:

    - Environment files containing real credentials are ignored by Git.
    - Authentication checks are performed on protected routes.
    - Input validation uses Zod.
    - Upload extensions and MIME types are checked.
    - Upload sizes are limited.
    - Database relationships use foreign keys.
    - Duplicate likes and follows are prevented by unique constraints.
    - The production Docker container runs as a non-root user.
    - Docker Compose uses health checks for PostgreSQL.
    - API errors are returned explicitly instead of silently succeeding.
    - Public discovery only returns active and public projects.

Before production deployment, the following should be reviewed:

    - Replace all local Docker passwords.
    - Use managed secret storage.
    - Rotate exposed or previously shared credentials.
    - Add rate limiting to public and authenticated APIs.
    - Add stricter file content validation and malware scanning.
    - Move uploads to object storage such as S3 or Supabase Storage.
    - Configure production Clerk domains and webhook secrets.
    - Add database backups and monitoring.
